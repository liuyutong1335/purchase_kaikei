# Implementation Notes — FEAT-PURCHASEKAIKEI

日付: 2026-09-10 / 作成: AI agent (Claude Code)

## v2 変更（kaikei-api 連携の廃止 → 内蔵会計エンジン）

v1 は検収・支払時に kaikei-api（FastAPI・port 8000）へ HTTP POST する構成だった。
実機検証で (1) kaikei-api 未起動時に検収・支払・会計ビューが使えない、(2) kaikei-api の
エラー応答時に Express 4 が uncaught exception でプロセスごと落ちる（修正はした）など、
**外部プロセスへの依存が研修用途では恒常的な故障ポイントになる**と判断し、ユーザーの
指示により v2 で方針転換した。

1. **会計エンジンの内蔵**: `store/journal.js` を新設。仕訳台帳（`entries` 配列）を
   data/purchases.json に蓄積し、試算表・総勘定元帳は要求のたびに計算する（結果の
   実体を持たないため帳簿ずれが構造的に起きない）。科目マスタは kaikei-api と同じ
   11 科目体系を維持。
2. **整合の保証方法が変わった**: v1 は「POST 成功が遷移の完了条件」だったが、v2 では
   仕訳と購買データが**同じ JSON・同じ書き込み時**に保存されるため、常に整合する。
   検収・支払は常に成功する（外部障害という失敗モードが消えた）。
3. start-all.bat / stop-all.bat を削除（ダブル起動が不要になった）。ポートは 3010 のまま。
4. テスト: モック kaikei-api を廃止し、エンジンの単体テスト（貸借一致・残高繰越・
   部門フィルタ）と会計 API の結合テストを追加。19 → 22 件。

## 設計判断

### 1. 試算表・元帳を「計算」で提供する
kaikei-api も同じ方式（要求のたびに仕訳から集計）であり、口径を揃える。
残高 = normal_side に応じて 借-貸 または 貸-借。部門指定でも貸借一致が保たれる。

### 2. v1 データとの互換
`#load()` で `entries` が無い旧ファイルに `entries: []` / `counters.entry = 0` を補う。
