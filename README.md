# 購買会計システム（研修用）

> このブランチ（`feature/kaikei-linkage`）は v4: v2（main・独立アプリ）に **kaikei-api ミラー連携（Outbox 方式）**・**SQLite 永続化**・**管理会計（kanri-dwh）連携** を追加した版です。
> 連携はオプション — 相手が無くても購買・財務会計は全機能動きます。

Tecnos-STRIDE (SDD) フローで開発。**purchase-management（購買管理）** を土台に、
**会計機能（仕訳・残高試算表・総勘定元帳）を内蔵した独立アプリ**。

## データベース構成（SQLite × DuckDB — なぜ 2 つあるのか）

このシステム（+連携先）には **2 種類のデータベース**があり、役割が違う。混同しやすいので整理する。

| システム | DB | ファイル | 役割 | 書き込みパターン |
|---|---|---|---|---|
| purchase-kaikei（本アプリ） | **SQLite** | `data/purchase-kaikei.db` | 購買業務の正本（申請・支払予定・仕訳台帳・Outbox キュー） | 逐筆トランザクション（OLTP） |
| kaikei-api | SQLite | `kaikei.db`（あちら側） | 会計台帳（会社の公式帳簿・ミラー先） | 逐筆トランザクション（OLTP） |
| kanri-dwh | **DuckDB** | `kanri-dwh/kanri.duckdb` | 経営 KPI 用の分析 DWH（星型スキーマ） | バッチ取込（ETL・冪等） |

### データの流れ（管理会計画面の数字の旅）

```
① 購買の検収・支払
   → 仕訳を SQLite（purchase-kaikei.db）に計上 ←【出生地・正本】
② kaikei-api にミラー送信（Outbox・自動再送）
   → 会計台帳（kaikei.db）に蓄積
③ kanri-dwh が ETL で取込（POST /api/etl or start.bat が自動実行）
   → DuckDB（kanri.duckdb）に星型スキーマで蓄積
④ 管理会計ビューが DuckDB の KPI（部門別損益・資金推移など）を表示
```

つまり管理会計ビューの数字は、**SQLite（購買）で生まれ、会計台帳を経て、DuckDB に着いたもの**。
生の仕訳を分析にそのまま使わず、公式台帳（kaikei-api）を**突合してから** DWH に取り込むのは、
「部門の自己申告ではなく公式帳簿を正とする」ため — ここが 1 つの DB にまとめない最大の理由。

### なぜ 1 つにまとめないのか

- **書き込みパターンが違う**: 購買業務は逐筆トランザクション（SQLite の得意技）、
  経営分析は大量集計（DuckDB の得意技）。互いの不得意を無理にさせない。
- **対照（突合）のため**: 台帳が 1 つだと「合っているか確認する」構造そのものが消える。
  独立した帳簿があるからこそ、突合（reconcile）に意味がある。
- **現実の会社と同じ構造**: 部門システム → 総帳（ERP） → 経営 DWH は別システムであり、
  Outbox・ETL・対账という「システム間連携」こそ本研修の主題。

## 仕組み

| 購買側の操作 | 自動計上される仕訳 |
|---|---|
| 検収（数量 q・単価 p） | 借方: **5110 仕入高** / 貸方: **2110 買掛金**　金額 = q × p |
| 支払実行 | 借方: **2110 買掛金** / 貸方: **1120 普通預金**　金額 = 支払額 |

- 申請に**部門**（D10/D20/D90・既定 D90）を付け、仕訳の department に引き継ぐ。
- 永続化は **SQLite**（`data/purchase-kaikei.db`・Node 内蔵の `node:sqlite`、依存追加なし）。購買・支払予定・仕訳台帳（`journal_entries` + `journal_lines`）・未同期キュー（`pending_links`）を**同一トランザクション**で書き込むため**常に整合**する。
- v3 までの `data/purchases.json` がある場合は、初回起動時に自動で SQLite へ取り込みます（JSON ファイルはそのまま残ります）。
- 残高試算表・総勘定元帳は仕訳台帳から**その都度計算**（計算結果の実体を持たないので帳簿ずれが起きない）。
- 「財務会計」ビューで残高試算表（11 科目すべて・残高 0 含む・貸借一致）と総勘定元帳（残高繰越）を照会できる。

## 起動

```bash
npm install
npm start        # → http://localhost:3010（会計エンジン内蔵・これだけで完結）
```

**`start.bat` 推奨** — 連携先（kaikei-api・kanri-dwh）が未起動なら自動で起動し、ETL（DWH 取込）まで実行してから本アプリを立ち上げる。ダブルクリックだけで 3 システム連携が動く。連携先が無ければ警告を出して縮退起動（購買・財務会計は通常どおり）。

停止は `stop.bat`（本アプリのみ）+ `Kaikei-API-Kanri-DWH\停止.bat`（連携先の Python サーバー）。

## kaikei-api ミラー連携（v3・オプション）

- 検収・支払で計上した各仕訳を、**kaikei-api（FastAPI・port 8000）が稼働していれば自動でミラー送信**します（Outbox 方式。内蔵エンジンが常に正本）。
- kaikei-api が止まっていても**購買操作は一切止まりません**。未送信の仕訳はキューに保持され、**復帰を検知すると自動で再送**します（30 秒間隔の自動再送タイマー＋起動直後の 1 回。検収・支払のたびにも即時送信を試みます）。財務会計画面で「未同期 n 件」と表示され、**「未同期を再送信」ボタン**の手動再送も可能です。
- 同期済みの仕訳には kaikei-api 側の採番 id（`kaikeiEntryId`）が記録され、向こうの総勘定元帳でも追跡できます。
- URL は `KAIKEI_API_URL` 環境変数で変更可（既定 `http://localhost:8000`）。

## 管理会計（kanri-dwh 連携・オプション）

3 システムが 1 本のチェーンでつながります:

```
purchase-kaikei ──仕訳ミラー──▶ kaikei-api(:8000)
      ▲                            │
      │ KPI 表示                    │ kanri etl（台帳を取込）
      │                            ▼
      └─ 経営ダッシュボード ◀── kanri-dwh(:8100・DuckDB)
```

- ナビの「**管理会計**」で、kanri-dwh（管理会計 DWH）の **部門別損益・月別売上・科目別費用・資金推移** と突合状態を表示します（このアプリが全システムの入り口になる）。
- **「DWH に取込（ETL）」ボタン**で kanri-dwh の取込（`POST /api/etl`・CLI と同じ経路・冪等）を起動。kaikei-api にミラー済みの仕訳が DuckDB に反映され、KPI に反映されます。
- kanri-dwh が止まっていても購買・財務会計ビューは通常どおり。ダッシュボードにその旨を表示するだけです。
- URL は `KANRI_DWH_URL` 環境変数で変更可（既定 `http://localhost:8100`）。

## 使い方

1. 「新規申請」から申請（申請者・品目・数量・単価は必須、部門を選択）
2. 「申請一覧」の「詳細」からアクション実行: 承認 / 却下（理由必須）/ 再申請 / 発注 / **検収（この時点で仕訳計上）**
3. 「支払予定」で支払実行（**この時点でもう 1 本仕訳を計上**）
4. 「財務会計」ビューで残高試算表・総勘定元帳を照会 — 検収・支払した仕訳がそのまま反映される

## 状態遷移

```
申請済み →(1 段承認)→ 承認済み → 発注済み →(分割検収・その都度仕訳)→ 全量検収済
    └→ 却下 →(再申請)→ 申請済み
検収ごとに支払予定(payable)を計上: 支払予定 →(支払実行・仕訳計上)→ 支払済み
```
